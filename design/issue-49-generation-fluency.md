# Issue #49：生成速度与流畅度设计

版本：`performance-generation-fluency/v1`  
父任务：[#18](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/18)  
实现交接：[#27](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/27)

本文回答“开始输出之后快不快、中间会停多久”。只测单请求、客户端可观察的正文生成体验，不用并发吞吐替代单请求速度，不把传输分包数量当成 token 数，也不评价生成内容质量。

## 1. 固定条件

| 条件 | 固定值 |
| --- | --- |
| 输入 | 约 512 token 的受控短文本 |
| 目标输出 | 1,024 token |
| 响应模式 | 流式，单并发 |
| 预热 | 3 次，等待完成，不计正式指标 |
| 正式请求 | 40 次 |
| 单请求超时 | 120 秒 |
| 正式组最长时间 | 80 分钟 |

提示词直接给出内容要求，避免复杂推理、工具调用或业务知识造成任务难度差异。模型、服务、客户端版本、输出设置和输入指纹在 40 次请求中固定。

## 2. 事件分层

客户端同时保存原始事件序列和语义分类：空事件、推理事件、正文内容事件、收尾/终止事件。网络读取块、SSE 事件和正文增量严格区分；底层一次读取多个事件不能被算成一个正文块。

每个正文事件记录到达时间、正文 Unicode 码点数、可用 token 计数来源和累计值。推理块不进入正文速率；首个正文块之前的等待只进入正文首响背景指标，不进入正文生成区间。

## 3. 指标口径

### 3.1 正文字符速率

对正文首块到正文末块之间的 Unicode 码点总数除以时间差，单位为字符/s。首块只有一个、时间差为零或没有正常结束时不计算，避免无限值或伪造速度。字符数使用 Unicode 码点，不使用字节数。

### 3.2 正文 token 速率

只有可信、可分离的正文区间 token 计数才展示。服务 usage 若只给 completion 总量且包含推理、终止或其他内容，不直接减 1 或按片段分词相加；无法确认正文区间计数时留空。若另有包含等待的全请求 token 产出率，必须使用不同名称，不能写成正文 token 速率。

### 3.3 正文块间隔

对相邻正文事件的到达时间差计算中位数、P95、间隔数量和请求数。空事件、推理事件和收尾事件不作为正文间隔。没有至少两个正文事件的请求标记“不可计算”，不称零停顿。

### 3.4 每请求最大停顿

每个请求取正文相邻事件间隔的最大值，再对请求级最大值计算中位数和最大值。该统计与所有间隔的分布分开保存；不能把上千个正文块声称为上千次独立请求。

## 4. 长度入组和异常

目标输出不足的请求仍保留在完整请求和异常统计中；只有满足预先固定的正常结束与目标长度条件的请求才进入“目标长度速度”视图。自然结束且输出短于目标的请求标记短答，不当作 1,024 token 速度。

部分正文后断开、缺终止事件、客户端主动停止或超时分别记录。客户端主动停止不是模型失败，也不是正常结束；无足够正文事件时保留首响/完整耗时和限制，但不计算流畅度指标。

## 5. 统计与客户展示

正式结果至少展示：请求数、正常完整数、目标长度入组/未入组数、正文字符速率中位数/P95、可用 token 速率中位数/P95、正文块间隔中位数/P95、每请求最大停顿中位数/最大值、正文首响、完整耗时、短答、超时、截断和取消数。

没有已确认的用户体验阈值，不设置红绿合格灯，不把指标转成硬件性能或生产 SLA。首块包含 10 个 token、推理持续输出、一次性到达全文和全请求等待都必须在详情中说明边界。

## 6. 受控验收案例

| 案例 | 行为 | 预期 |
| --- | --- | --- |
| FLU-01 | 多个正文事件均匀到达 | 计算字符速率和正文块间隔 |
| FLU-02 | 首块包含多个字符/token | 不机械减 1，不虚构正文 token 速率 |
| FLU-03 | 全文一次性到达 | 保留完整耗时，间隔与速率标记不可计算 |
| FLU-04 | 推理块先于正文 | 推理等待不进入正文速率 |
| FLU-05 | 输出 100 token 后自然结束 | 记为正常短答，不进入目标长度速度视图 |
| FLU-06 | 正文中途断开或缺终止 | 不判完整通过，保存截断证据 |
| FLU-07 | 客户端主动停止 | 记录取消来源，不归因模型失败 |
| FLU-08 | 正文块跨网络读取边界 | 以协议事件组装，不依赖底层分包 |

## 7. 证据结构

每个请求保存固定条件、输入指纹、原始事件、事件类型、到达时间、正文增量、Unicode 码点数、token 计数来源、首响/完整时间、终止原因、间隔列表、请求级最大停顿、目标长度入组、超时/截断/取消原因和脱敏响应。聚合指标必须能从请求记录重算；API key 不进入证据。

## 8. 验收标准

| AC | 检查 | 预期 |
| --- | --- | --- |
| AC-01 | 固定负载和样本 | 单并发、预热 3 次、正式 40 次、目标输出 1,024 token、120 秒超时明确 |
| AC-02 | 正文事件分类 | 正文、推理、空事件、收尾和网络读取块不混淆 |
| AC-03 | 字符/token 速率 | 字符速率使用 Unicode 码点；token 速率仅在正文区间可信时展示 |
| AC-04 | 块间隔/最大停顿 | 所有间隔和请求级最大停顿分开统计，零间隔不伪造无限速度 |
| AC-05 | FLU-03-FLU-07 | 一次性到达、短答、截断、超时和取消不被包装成流畅通过 |
| AC-06 | 证据重算 | 原始事件、计数来源、入组条件和聚合指标可重算 |
| AC-07 | 范围审查 | 不把单请求速度扩大为并发吞吐、质量、硬件性能或生产 SLA |

本设计只形成 #18 的生成速度输入，不代表执行器已实现或任何真实模型已完成流畅度测量。
