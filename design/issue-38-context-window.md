# Issue #38：模型最大上下文检测设计

版本：`specification-context-window/v1`  
关联：[#16](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/16)  
交接：[#25](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/25)

本文只定义“当前服务在固定条件下可接受的最大输入上下文范围”。它不测长材料理解、最长输出、输出参数生效、能力跑分、性能或 Agent 可用性。

## 1. 计量口径

结果必须同时保存四个量：

| 量 | 定义 | 缺失时的处理 |
| --- | --- | --- |
| `input_tokens` | 请求中 system/user/assistant/tool 消息按目标服务 tokenizer 计算的 token 数 | 没有可信 tokenizer 时不得写成精确 token；只记录估算并标记 `inconclusive` |
| `reserved_output_tokens` | 固定为 256 的输出预留 | 不得把预留量并入已验证输入下界而隐藏 |
| `window_claim` | 只有服务明确拒绝且排除其他限制后才可声称的窗口边界 | 不能由模型自述、文档标称或最高成功档生成 |
| `verified_input_floor` | 已取得正常完整响应的最高输入档 | 永远只写成已验证下界，不改名为最大窗口 |

首选服务返回的 `usage.prompt_tokens` 作为实际计数来源，并记录 tokenizer/计数器版本。客户端估算只能用于构造下一档，不能单独支撑精确容量结论。

## 2. 输入构造和固定条件

使用可重复的中文材料生成器：固定头部、固定段落模板、唯一位置标记和尾部校验标记。材料只用于占用上下文，不要求模型理解内容。每次请求保持相同 system 消息、temperature=0、`max_tokens=256`、非流式模式；只改变填充段数量。

探测记录必须保存输入指纹、消息角色顺序、估算 token、服务 usage、输出预留、模型、协议、请求体大小和运行环境。禁止用字符数直接充当 token 数。

## 3. 探测算法

1. 从 1,024 token 起按 1,024 递增，直到取得一次明确成功和一次疑似限制，或达到预先声明的安全上限。
2. 发现失败后，在最近一次成功和失败之间二分；每个候选档最多进行 1 次初测。
3. 对最终成功边界和最终失败边界各复核 2 次，输入、设置和计数版本完全一致。
4. 只有成功档三次均正常结束、失败档三次均出现同一可归因容量拒绝，并排除超时/限流/网关体积限制/客户端截断，才可写 `window_claim`。
5. 精度等于最终成功与最终失败的 token 间隔；若服务计数来源不可比，结果为 `inconclusive`，只保留已验证下界。

执行上限默认 20 个候选档、单次超时 300 秒。达到上限仍无可靠失败边界时停止，不继续扩大请求成本，也不宣称上限。

## 4. 异常分流

| 观察 | 处理 | 是否影响容量结论 |
| --- | --- | --- |
| HTTP 400 明确说明上下文超限，且请求体/代理限制已排除 | 候选失败边界，可进入复核 | 可以 |
| 认证、权限、429、5xx、连接中断 | 标记执行异常，按传输规则重试 | 不可以 |
| 网关提示请求体过大或本地代理拒绝 | 标记环境限制，不作为模型窗口 | 不可以 |
| 响应提前结束、finish reason 缺失或流被客户端截断 | 标记静默截断风险，不能作为成功/失败边界 | 不可以 |
| 返回模型自述或固定标称值 | 仅作为非测量说明保存 | 不可以 |
| usage 缺失或不同档计数口径变化 | 结果不可精确比较 | 不可以 |

若成功响应内容被静默截断，必须通过 finish reason、完整响应和尾部校验标记检查；不能把“收到 HTTP 200”视为成功完成。

## 5. 结果状态和客户展示

- `verified_range`：取得可复核的成功输入范围，但仍只表示当前服务和条件。
- `inconclusive`：存在成功响应但计数、终止或失败原因不足，或仅找到下界。
- `unsupported`：服务明确声明该请求模式不支持，不等同于上下文窗口不足。
- `failed`：有效响应违反完整性规则；不用于代替容量异常。

客户主视图优先展示：`最大上下文：未测出上限`、`已验证输入下界：N tokens`、`测量精度：M tokens`。详情展示计数来源、输出预留、成功/失败两侧样本、复核次数和停止原因。任何下界都不得显示在“最大上限”字段中。

## 6. 受控验收样例

| 样例 | 受控服务行为 | 预期 |
| --- | --- | --- |
| C01 | 在 8,192 token 拒绝并稳定返回上下文超限 | 定位 8,192 附近边界，保存两侧复核和精度 |
| C02 | 所有档位成功直到安全上限 | 显示未测出上限，只保存最高成功下界 |
| C03 | 认证错误和 429 混合出现 | 不生成容量边界，保留传输异常和重试证据 |
| C04 | 代理按字节拒绝大请求 | 标记网关限制，不归因模型窗口 |
| C05 | HTTP 200 但响应在尾部标记前截断 | 不计为成功边界，标记静默截断风险 |
| C06 | usage 缺失或 tokenizer 口径改变 | 不报告精确 token 上限，保留估算和证据缺口 |

## 7. 验收标准

| AC | 检查 | 预期 |
| --- | --- | --- |
| AC-01 | 核对范围 | 只检测最大上下文 token，不改变其他规格类别 |
| AC-02 | C01 已知边界 | 探测、二分、复核和精度均可被另一人复现 |
| AC-03 | C02 无失败边界 | 明确显示未测出上限，不冒充最高成功档为上限 |
| AC-04 | C03-C06 异常与截断 | 不把环境、网关、截断或计数问题归为容量边界 |
| AC-05 | 证据审查 | 请求条件、计数来源、输出预留、两侧结果、复核和停止原因完整 |
| AC-06 | 客户结果审查 | 下界、上限、精度和不可测量状态字段不混用 |

本设计不代表真实模型已经完成容量测量。实施时必须以版本化计数器和受控服务验收记录为准。
