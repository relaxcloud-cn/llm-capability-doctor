# Issue #40：流式输出测试设计

版本：`specification-streaming-output/v1`  
关联：[#16](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/16)  
交接：[#25](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/25)

本文冻结普通文本流式输出和工具调用流式输出两项检测。两项分别记录结果；不测首 token 延迟、吞吐、并发、稳定性、工具执行、回传或 Agent 规划。

## 1. 统一请求与事件模型

请求使用 Chat Completions、`stream=true`、`temperature=0`，每个场景使用短的受控提示和唯一首尾标记。测试客户端必须保存原始响应字节、解析后的事件顺序、事件时间、终止事件和组装结果。

必须区分三层：

1. HTTP/SSE 传输块：网络读取边界，不代表模型内容增量。
2. 协议事件：每个可解析的 `data:` 事件及其 JSON 内容。
3. 语义增量：`choices[].delta.content`、工具调用 ID/name/arguments 的实际变化。

网络一次读取到两个事件，或一个事件跨越多个读取块，都不能改变语义事件计数。

## 2. 普通文本流式输出

### 固定样例

| 样例 | 受控要求 | 通过条件 |
| --- | --- | --- |
| ST01 | 返回带唯一首尾标记的短文本 | 收到至少一个可识别内容增量，按顺序组装出完整原文，并收到正常结束信号 |
| ST02 | 在内容前后插入空内容事件 | 空增量被保留为合法事件，不导致失败；非空内容仍完整组装 |
| ST03 | 多个内容分片跨网络块到达 | 依据协议事件组装，不依赖底层读取边界 |
| ST04 | 结束事件缺失 | 标记 `inconclusive` 或 `failed`，不得因已收到部分文字而通过 |
| ST05 | 在尾部标记前断开 | 组装不完整；保存截断证据，不判定正常结束 |

完整通过要求：内容增量可解析、顺序正确、首尾标记完整、终止原因可识别且客户端未主动停止连接。收到 `[DONE]` 但没有完整内容也不能通过。

## 3. 工具调用流式输出

### 固定工具

使用 #36 冻结的 `lookup_weather` 工具，另提供 `lookup_air_quality` 作为多调用区分。请求不执行工具，不发送工具结果，不要求模型续答。

### 固定样例

| 样例 | 分片安排 | 通过条件 |
| --- | --- | --- |
| STT01 | 一个工具调用，name 和 arguments 分多事件返回 | 依据 choice/index/call ID 归组，最终 name 正确，arguments 拼接后为合法 JSON |
| STT02 | arguments 在字符串边界中间切片 | 单个片段可以是非法 JSON；全部片段拼接后合法才判定 |
| STT03 | 同一响应两个调用交错返回 | 按调用 ID 分别拼接，两个调用名称和参数不串位 |
| STT04 | 工具调用后正常结束 | 工具信息完整，收到正常终止事件；不执行工具 |
| STT05 | 调用参数尾部断开 | 保留已收到片段，标记不完整或不可解析，不判定通过 |
| STT06 | 只有普通文字、没有工具增量 | 在工具调用场景中为有效未满足或 `inconclusive`，不能用文本流通过替代 |

工具调用通过必须同时满足：调用身份可归组、名称完整、参数片段按顺序拼接、最终 JSON 可解析、必填字段和类型符合固定 schema、正常结束可验证。每个参数片段无需单独合法 JSON。

## 4. 次数、复核和停止

每个固定样例初测 1 次。有效响应违反完整性或调用 schema 时，对同一输入和设置追加最多 2 次复核，并保留首次有效失败；超时、连接中断、限流和解析前无有效响应最多追加 2 次重试。复核与重试独立计数，不因一次成功覆盖之前的失败。

客户端主动取消、用户停止或达到外部超时必须记录停止原因；客户端停止不计为服务正常结束，也不应被写成模型失败。

## 5. 状态判定

| 状态 | 条件 |
| --- | --- |
| `pass` | 对应场景的语义增量、完整组装、协议终止和 schema（工具场景）均满足 |
| `fail` | 有效且未被客户端主动停止，但内容/调用完整性或固定 schema 明确违反 |
| `unsupported` | 服务明确拒绝流式模式；不能由网络异常推导 |
| `inconclusive` | 没有足够有效事件、终止原因、完整计数或存在无法排除的传输/解析异常 |

结构字段缺失只有在造成可观察的增量、组装或结束问题时才影响本项能力；单纯结构差异交给基线模块。

## 6. 证据结构

每个样例至少保存：请求设置和工具 schema 指纹、原始字节、SSE 事件原文及顺序、事件解析错误、语义增量、按内容/调用 ID 的组装过程、终止事件、客户端停止原因、复核/重试关系、最终状态和限制。API key 不进入原始证据或报告。

## 7. 受控验收案例

| 案例 | 检查点 | 预期 |
| --- | --- | --- |
| R01 | 内容被拆成多个事件和多个读取块 | 组装文本完整，底层分块数量不影响结果 |
| R02 | 空内容事件夹在有效内容之间 | 保留空事件但判定不失败 |
| R03 | 工具 arguments 分成非法 JSON 片段 | 拼接后合法则可通过 |
| R04 | 两个调用按 ID 交错 | 每个调用独立组装，不串参数 |
| R05 | 缺 `[DONE]`、尾部断开或参数不完整 | 不判完整通过，证据标记截断/未完成 |
| R06 | 客户端主动停止 | 记录客户端停止，不归因模型失败 |
| R07 | 服务明确拒绝 `stream=true` | `unsupported`，不混入网络失败 |

## 8. 验收标准

| AC | 检查 | 预期 |
| --- | --- | --- |
| AC-01 | ST01-ST03 | 识别语义增量并正确组装，不依赖网络读取边界 |
| AC-02 | STT01-STT04 | 工具调用按 ID 归组、参数拼接、schema 和结束可判定 |
| AC-03 | STT02 | 单个参数片段不要求独立 JSON，最终拼接结果才进入解析 |
| AC-04 | ST04-ST05、STT05、R05-R07 | 截断、解析、客户端停止、unsupported 和 inconclusive 不混淆 |
| AC-05 | 证据审查 | 原始事件、组装轨迹、终止和复核/重试完整可追溯，凭据脱敏 |
| AC-06 | 范围审查 | 不把流式通过扩大到非流式工具、性能或 Agent 闭环 |

本设计完成后仍需由后续执行任务接入真实 SSE 解析和受控 fixture；它不代表真实服务已完成流式测试。
