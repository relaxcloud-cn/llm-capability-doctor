# Issue #51：响应等待：正文首响与完整耗时设计

版本：`performance-response-waiting/v1`  
父任务：[#18](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/18)  
实现交接：[#27](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/27)

本文回答“请求发出后多久开始看到正文、多久完整结束”。它区分流式与非流式，不评价答案正确性，不把第一个空事件、角色事件或纯推理片段当成正文首响，也不把完整返回时间反推成非流式首 token 时间。本轮只冻结产品口径，不实现、不实测、不开展真实服务验收。

## 1. 客户结果

| 模式 | 主指标 | 辅助信息 |
| --- | --- | --- |
| 流式 | 正文首响中位数/P95；完整耗时中位数/P95 | 有效样本数、正常完成/正式派发数、异常数量、实际输入/输出长度 |
| 非流式 | 完整耗时中位数/P95 | 首响显示“不适用”，不得用完整返回时间冒充首 token 时间 |

没有业务响应时限时，不自动判定合格、不可用或达标。主视图必须同时显示模式、输入/输出条件、并发、预热、正式次数、计时来源和异常分母；完整原始时间线、环境和请求条件放在详情中。

## 2. 固定负载与执行窗口

| 条件 | 固定值 |
| --- | --- |
| 输入 | 约 512 token 的受控短文本 |
| 目标输出 | 256 token；只作为长度目标，不保证每次达到 |
| 并发 | 1 |
| 响应模式 | 流式、非流式分别执行 |
| 预热 | 每种模式 3 次，等待终态，不计入正式指标 |
| 正式请求 | 每种模式 40 次 |
| 单请求超时 | 120 秒 |
| 模式正式组最长时间 | 80 分钟 |
| 重试 | 不自动重试，不因失败补发替代正式样本 |

两种模式使用同一模型、输入材料、输出设置和客户端版本；请求封装与传输模式的必然差异必须记录。两次模式的实际输出内容和长度不要求相同，不得因内容不相同而删除一方样本。

计时从请求交给 HTTP 客户端、开始发送前的 `t_send` 开始，不包含调度器排队。连接建立、服务端排队和响应传输均属于客户端可观察等待，应包含在指标内。

## 3. 时间线与终态

每个正式请求至少保存以下时间点：

| 时间点 | 定义 | 是否进入主指标 |
| --- | --- | --- |
| `t_send` | HTTP 客户端开始发送请求前的单调时钟时间 | 所有耗时起点 |
| `t_first_event` | 收到第一个可解析协议事件，可能为空或只有角色字段 | 仅详情 |
| `t_first_reasoning` | 收到首个可识别推理片段（若协议能区分） | 仅详情 |
| `t_first_visible` | 收到第一个包含非空白正文字符的片段 | 流式正文首响 |
| `t_complete` | 正常完成证据已收到且响应体消费结束 | 流式/非流式完整耗时 |
| `t_error` | 收到明确错误或连接以错误终止 | 异常耗时，非成功分布 |
| `t_timeout` | 客户端保护超时触发 | 超时耗时，非成功分布 |
| `t_cancel` | 客户端或用户主动停止 | 取消耗时，非成功分布 |

请求终态必须为 `completed`、`error`、`timeout`、`truncated` 或 `cancelled` 之一。只有 `completed` 且有完整消费证据的请求进入完整耗时成功分布；异常请求保留实际终止耗时和原因，但不得被静默丢弃。

## 4. 流式口径

### 4.1 正文首响

流式正文首响为：

```text
first_visible_latency = t_first_visible - t_send
```

`t_first_visible` 必须对应第一个包含至少一个非空白、用户可见正文字符的语义事件。以下事件不能结束正文等待：

- 空 SSE/协议事件、仅有 `role` 或空 `content` 的事件；
- 只有推理、思考或内部通道内容的事件；
- 工具调用字段、终止原因、usage 或 `[DONE]` 事件；
- 网络读取块本身，除非组装后形成可识别的正文事件。

正文首响只要求出现正文，不要求请求最终正常完成。若首字已经到达但随后超时、断开或取消，必须同时保留首响时间和异常终态，不能把该请求算入完整成功数。

### 4.2 完整耗时

流式完整耗时为：

```text
streaming_completion_latency = t_complete - t_send
```

正常完成必须同时满足协议终止证据和响应消费结束。仅收到正文、收到 stop 字段但未消费完响应、或收到 `[DONE]` 前连接断开，都不能标为 `completed`。如果服务协议没有可验证的终止证据，应标为终态不完整，并在限制中说明。

## 5. 非流式口径

非流式只记录完整耗时：

```text
non_streaming_completion_latency = t_complete - t_send
```

响应体完整消费、状态成功、响应结构可解析且无传输截断时才进入 `completed` 分布。非流式正文通常在响应体消费完成后才对客户端可见，因此不定义可观测的正文首响；报告显示“首响：不适用”，不得把 2 秒完整返回写成“首 token 2 秒”。

如果非流式响应状态为成功但 JSON 被截断、正文为空或结构无法解析，保留终止耗时，按 `truncated` 或 `error` 记录，不能混入正常完整耗时分布。是否有正文内容与是否完整终态是两个字段。

## 6. 统计、分母与展示

每种模式分别聚合，不合并流式和非流式的首响或完整耗时。报告至少包含：

| 字段 | 规则 |
| --- | --- |
| 正式派发数 | 计划实际交给 HTTP 客户端的请求数 |
| 首响有效数 | 流式出现 `t_first_visible` 的请求数；非流式为不适用 |
| 完整成功数 | 终态为 `completed` 的请求数 |
| 首响 P50/P95 | 仅对有正文首响的流式请求计算，显示有效样本数 |
| 完整耗时 P50/P95 | 仅对正常完成请求计算，显示成功样本数；异常另列 |
| 异常数量 | 按 error/timeout/truncated/cancelled 分类，不隐藏 |
| 长度信息 | 实际输入/输出 token、目标输出、短答和截断单列 |

百分位计算方法、时间单位和舍入规则沿用 #18 共用指标字典；原始值使用单调时钟的毫秒或更高精度保存。有效样本不足时展示中位数、范围、样本数和“P95 不可用”原因，不伪造 P95。失败、超时和取消不能被过滤后包装成“40 次稳定延迟”。

## 7. 受控验收案例

| 案例 | 观察 | 预期 |
| --- | --- | --- |
| WAIT-01 | 空事件后收到推理，随后出现正文 | 首响从正文事件计算，空事件和推理只进详情 |
| WAIT-02 | 首字很快，随后请求超时 | 保留首响和超时终态；进入首响分布，不进入完整成功分布 |
| WAIT-03 | 正文正常结束并消费完流 | 进入流式首响和完整耗时成功分布 |
| WAIT-04 | 多个网络读取块拼成一个正文事件 | 按协议事件计时，不把读取块数量当正文事件数 |
| WAIT-05 | 非流式 2 秒返回完整 JSON | 完整耗时 2 秒；首响为“不适用” |
| WAIT-06 | 非流式成功状态但响应体截断 | 记录截断耗时，不进入完整成功分布 |
| WAIT-07 | 只有 12 个流式首响有效样本 | 展示 P50、范围和 `12/40`；P95 按共用最低样本规则处理或标不可用 |
| WAIT-08 | 请求被 401/403/429 拒绝 | 保留错误时间和原因，不归因成模型响应变慢 |

## 8. 证据结构

每条请求记录至少包含：固定负载指纹、模式、模型和服务标识、客户端版本、`t_send`、各可观察时间点、单调时钟来源、协议事件分类、响应消费状态、终态、错误/超时/截断/取消原因、实际输入/输出长度、请求 ID 和脱敏原始证据。API key、Authorization header 和完整敏感正文不得进入报告证据。

聚合报告必须能从请求级记录重算：首响有效数、完整成功数、P50/P95、异常分类和长度覆盖。原始事件序列需要保留足够信息以解释“空事件/推理/正文/收尾”的判断；不要求保存未脱敏响应。

## 9. 设计反例与边界

| 观察 | 正确表达 | 禁止表达 |
| --- | --- | --- |
| 第一个事件为空，1.2 秒后出现正文 | 正文首响 1.2 秒 | 第一个事件即首响 |
| 首响后最终超时 | 首响已观察到，完整请求超时 | 完整耗时等于首响，或完整成功 |
| 非流式 2 秒返回 | 完整耗时 2 秒，首响不适用 | 非流式首 token 2 秒 |
| 40 次中 2 次超时 | 成功分布 38 个，全请求状态 40 个 | 删除 2 次后称 40 次稳定 |
| 只有一个正文事件 | 可保留首响和完整耗时，正文块间隔不适用 | 宣称无停顿或零间隔 |
| 429 导致提前停止 | 记录限流和实际观察窗口 | 写成模型延迟或性能失败 |

交接给 #27 的最小实现契约是：区分流式/非流式请求；记录单调时间线和语义事件；输出 `first_visible_latency`、`completion_latency`、终态和异常原因；保留请求级证据；按有效分母生成 P50/P95。#27 的实现不得自动重试、不得把异常请求隐藏在成功分布里，也不得以本设计单独宣称任何真实服务达标。
