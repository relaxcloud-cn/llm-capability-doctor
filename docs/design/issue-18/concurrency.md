# 并发承载：有限并发阶梯设计

父任务：#18。模块：模型性能实测。状态：设计草案，2026-09-09。本轮不实现、不实测、不开展验收，不授权对客户服务施加负载。

## 目标与范围

回答“同时处理多个请求时，等待、输出速度、完成量和异常怎样变化”。只测预设阶梯，不搜最大承载量，不换算最大用户数，不增加突发、恢复或开放请求速率场景。

## 客户结果

| 每档展示                       | 解释                                       |
| ------------------------------ | ------------------------------------------ |
| 目标并发与实际并发             | 同时在途请求数，不是用户数。               |
| 正文首响、完整耗时、单请求速率 | 保留不同档位下的单请求体验。               |
| 窗口完整请求吞吐               | 完整请求/s，异常与未完成请求不计成功吞吐。 |
| 完整比例和异常明细             | 派发队列追踪到终态，与窗口吞吐分母分开。   |

最高档只叫“最高已测并发”，不推导极限容量。用户没有确认性能要求时不评合格。

## 固定设计

流式输入约 512 token，目标输出 256 token。并发阶梯 1、2、4、8，顺序执行；每档按目标并发预热一轮并等待结束，档间空闲 10 s。

每档派发窗最多 120 s 或 300 次实际请求，先到为止；单请求总超时 120 s，窗口结束后最多排空 120 s。采用闭环：空槽补位，不承诺固定请求/s；记录实际并发曲线和客户端调度空隙。

窗口吞吐只统计窗口内正常结束的请求。派发截止后的排空完成单列，用于补齐该队列最终完整比例，不回填到窗口吞吐分子。提前达请求数上限时报告实际窗口，不声称已覆盖 120 s。

性能请求不自动重试。遇到 429、认证失效或共用保护停止条件，停止该档和自动升档，保留在途请求与异常证据；不通过重试掩盖错误。阈值属于保护条件，不是性能通过线。

## 设计反例

| 观察                             | 预期表达                                             |
| -------------------------------- | ---------------------------------------------------- |
| 并发配置 8，客户端实际只能维持 3 | 标记负载不足，不报告已验证并发 8。                   |
| 并发 4 遇到限流                  | 报限流与停止，不宣称模型最大并发是 4。               |
| 窗口后又完成 10 个请求           | 排空结果单列，不抬高原窗口吞吐。                     |
| 高并发时输出变短                 | 实际长度和目标达标比例同屏，不用短答制造高吞吐假象。 |
