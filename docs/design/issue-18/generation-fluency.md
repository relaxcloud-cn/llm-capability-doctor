# 生成速度与流畅度：正文速率与停顿设计

父任务：#18。模块：模型性能实测。状态：设计草案，2026-09-09。本轮不实现、不实测、不开展验收。

## 目标与范围

回答“开始输出之后快不快、中间会停多久”。只测客户端观察到的正文生成体验，不用全部并发请求的系统吞吐替代单请求速度，不把传输分包当 token。

## 客户结果

| 指标            | 展示约束                                                 |
| --------------- | -------------------------------------------------------- |
| 正文字符速率    | 字符/s，采用 Unicode 码点；不称 token 速度。             |
| 正文 token 速率 | 只有可信且可分离的首块后区间计数才显示；无数据留空。     |
| 正文块间隔      | 中位数、P95、间隔数量与请求数；不同于真实逐 token 时间。 |
| 每请求最大间隔  | 中位数及最大值；无足够块的请求标记不可计算。             |

保留正文首响、完整耗时和实际长度作为背景。没有已确认用户体验阈值，不用红绿合格灯定义“流畅”。

## 固定设计

流式输入约 512 token，目标输出 1024 token，单并发；预热 3 次，正式 40 次，单请求总超时 120 s，正式组最多 80 分钟。输入直接给出内容要求，避免复杂推理造成任务难度差异。

每个协议正文片段记录到达时刻，区别空事件、推理、正文与收尾。首块之后新增正文量除以首末正文块时间差，得到生成阶段速率；首块只有一个或时间差为零时不除零、不填无限速度。

不能先把每个片段单独分词再相加冒充完整 token 计数；completion 总量若含推理，也不能直接算正文速度。无法核实区间 token 时仍展示字符速率和块间隔；含等待的全请求 token 产出率若可计算，必须另名显示。

一项统计为所有内容间隔的分布，另一项为每请求最大间隔的分布；不把上千个块声称为上千次独立测量。目标输出不足的请求保留，目标长度速度视图显示入组与未入组数量。

## 设计反例

| 观察                         | 预期表达                                       |
| ---------------------------- | ---------------------------------------------- |
| 首块包含 10 个 token         | 不机械使用输出 token 总量减 1 计算后续速度。   |
| 全文一次性到达               | 有完整耗时，无可测间隔，不称零停顿或无限速度。 |
| 输出 100 token 就自然结束    | 记录正常短答，不当作 1024-token 测试速度。     |
| 推理先持续输出，正文尚未出现 | 不用推理块速率代替正文速度。                   |

## 交付边界

本子项交付速率、间隔、停顿的设计，不评价生成质量或服务端硬件性能。共用稿为 `docs/design/issue-18-performance-draft.md` 第 3–5 节，文档入口见 #18 评论。NVIDIA 指标为参考，不将其默认首块计数假设当作产品规则。
