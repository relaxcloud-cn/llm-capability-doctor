# 模型规格实测设计草案

版本：0.1。整理日期：2026-09-09。父任务：[#16](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/16)。

状态：已确认范围整理 + 测试方法提案。尚未实现检测器，尚未运行真实模型测试，尚未通过独立验收。本草案不能用来关闭 #16 或宣称 #25 已具备完整实现输入。

## 1. 阅读与决策规则

本模块回答当前接入服务“有没有这项基础能力、支持什么、限制在哪里”，不评价能力有多强，不产生模型能力总分或 Agent 任务结论。接口范围为 OpenAI 风格的 Chat Completions，不要求用户提供真实业务请求。

| 标记     | 含义                                                           |
| -------- | -------------------------------------------------------------- |
| 已确认   | 用户在本轮讨论中明确认可的范围或规则。                         |
| 设计提案 | 由设计工作补充的具体方法，需要受控验证；不冒充用户已逐条批准。 |
| 未收敛   | 需要设计或验收工作解决的问题，不默认采用工具行为填补。         |

后发生的用户明确决定优先于早期讨论。规范提供接口定义，不提供本产品的样本数、复核次数和通过线；这些属于产品规则或待校准提案。

## 2. 共用边界与结果

### 2.1 不跨模块推导

| 观察内容                       | 所属范围           | 不能推导的结论                               |
| ------------------------------ | ------------------ | -------------------------------------------- |
| 单个或多个工具调用生成正确     | 工具调用支持       | 不证明工具执行闭环、复杂规划或流式调用可用。 |
| 接口工具控制参数产生可观察效果 | 常用参数支持       | 不等于模型自主选择工具水平高。               |
| 返回字段、类型或层级不同       | 基线对比           | 不直接证明能力失败或整套服务不可用。         |
| 文本或调用增量及结束正常       | 流式输出支持       | 不证明速度、并发或长时间性能合格。           |
| 携带历史后能最小续答           | 消息与多轮输入支持 | 不证明服务自动保存历史或具有长期记忆。       |

### 2.2 主结果与详情

已确认工具调用的主结果如下，复核过程不占据客户主界面：

| 主结果 | 工具调用项的已确认含义                       |
| ------ | -------------------------------------------- |
| 通过   | 必需样例全部符合要求。                       |
| 未通过 | 存在有效调用生成错误；复核成功不抹去该错误。 |
| 未完成 | 因执行异常未取得足够结果。                   |

各子项独立呈现，不以单一总通过率覆盖差异。“未通过”只表示该项检测未通过，不能改写为完全没有工具能力或服务整体不可用。

设计提案：其他离散能力项目沿用简洁主结果，但必须先固定适用性和证据规则。不适用、未选择、无效执行分别保留原因，不伪装成通过；尚未纳入的项目不显示为不支持。上下文突出容量及“是否测出”，不强行替换为一个能力通过率。

未收敛：用户没有单独批准把“请求成功但生效证据不足”统一映射为“未完成”。正式规则需用受控案例检验其表达；本草案只确定它不能冒充“通过”或“参数失效”。详情记录请求接受性、有效观察、证据缺口，不增加新的能力得分。

### 2.3 最低证据包（设计提案）

每次实际请求有独立证据 ID，记录规则版本、样例版本、服务绑定、脱敏请求、固定设置、原始响应或流事件、结束状态、验收观察及复核关联。报告复用同一证据时保留相同 ID，不重复记为独立事故。

原始材料允许必要的传输解码，但不能经补括号、删除代码围栏或类型强制转换后把原始不合规结果判通过。该条是内部验收方法，不新增客户检测项。凭据不得进入材料，测试内容采用虚构数据。

## 3. 工具调用支持

### 3.1 已确认范围与判定

采用非流式 Chat Completions。题目明确提供工具和所有参数值，不考自主规划、工具选择优劣或业务推理。仅检查模型生成结果，不执行工具。

正确生成同时要求：接口可识别的工具调用、正确工具名称、可解析参数，以及符合题目要求的必填字段、类型和值。多个调用不能漏调用或串参数。

### 3.2 样例目录提案

每行是一种样例，准备 3 组预先固定的值。表内仅给出第一组的形状示意；三组完整请求和对应 schema 尚未冻结，不作为已交付的可执行题库。

| ID   | 覆盖               | 形状示意与验收重点                                                         |
| ---- | ------------------ | -------------------------------------------------------------------------- |
| TC01 | 字符串             | `record_city({"city":"Beijing"})`；名称、字段及原值对应。                  |
| TC02 | 数字               | `record_count({"count":3})`；数字与字符串不混同，不用隐式转换通过。        |
| TC03 | 布尔值             | `record_switch({"enabled":true})`；保留布尔类型。                          |
| TC04 | 枚举               | `record_mode({"mode":"fast"})`；schema 枚举范围和题目指定值同时满足。      |
| TC05 | 嵌套对象           | `record_place({"place":{"city":"Beijing"}})`；逐层验证。                   |
| TC06 | 数组               | `record_tags({"tags":["red","blue"]})`；验证元素类型和题目约定内容。       |
| TC07 | 同一工具调用两次   | 指定查询 Beijing 和 Shanghai，分别生成调用；不合并成未经定义的新参数形式。 |
| TC08 | 不同工具各调用一次 | 两个指定工具各一组直接给定的参数；检查对应关系。                           |

调用顺序是否有要求必须在样例中写明；没有顺序要求时按调用集合核验，保留重复次数，不误把合法换序算错。不宣称任意 schema 或任意数组、嵌套深度都支持。

设计提案：基础生成样例使用已记录的默认/自动工具设置，不借强制指定、严格输出配置来替代自然调用生成的证据。工具控制专项另见第 4 节。[R1]

### 3.3 已确认的次数与失败处理

1. 每种样例固定 3 组参数，每组初测 1 次；不代表统计可靠性保证。
2. 有效输出不合格时，对同一输入和设置追加 2 次复核。首次错误保留，之后成功也不改成通过。
3. 超时、限流等执行异常最多补试 2 次；取得有效响应按内容判定，始终无有效结果则未完成。
4. 复核与异常补试分开记录；一个样例失败不停止其他样例。

执行上限提案：将初测和两次复核分别视为一个有效观察位置，每个位置最多 3 次实际请求，复核失败不再递归触发复核。同一组输入最多 9 次实际请求；只有初测取得有效失败才启动两次复核。此上限是对两种重试叠加的设计解释，尚待受控测试验证，不冒充用户额外确认。认证失效等全局阻断另行停止，不为每个样例重复发送无效请求。

## 4. 常用参数支持

### 4.1 已确认清单

| 编号 | 参数                                                                | 检测目标                                           |
| ---- | ------------------------------------------------------------------- | -------------------------------------------------- |
| P02  | `tool_choice: "none"`                                               | 提供工具但禁止调用，检查控制效果。                 |
| P03  | `tool_choice: {"type":"function","function":{"name":"指定工具名"}}` | 指定具体工具，检查生成调用与指定项对应。           |
| P04  | `tool_choice: "required"`                                           | 至少产生一个工具调用，不评价选择优劣。             |
| P05  | `parallel_tool_calls: false`                                        | 一条响应最多一个工具调用，不检测实际工具并发执行。 |
| P06  | `stop`                                                              | 验证设置的停止标记作用，不评价输出质量或最大长度。 |

接口定义依据见 [R1]，P06 还须在正式规格冻结时归档 Chat Completions 参数参考。不因服务自称兼容就假定每个取值都适用。

P01 已撤销。P07–P13 不纳入：`n`、`logprobs`、`top_logprobs`、`reasoning_effort`、`frequency_penalty`、`presence_penalty`、`seed`、`logit_bias`、`temperature`、`top_p`。不为这些参数增加“仅检查是否接受”的隐性检测。

### 4.2 受控对照提案

每对请求固定输入、工具定义及其他设置，只改变被测控制。题目简单，所有工具所需值都直接提供。单次符合预期不足以排除偶合，以下对照需制作已知正常和故意忽略参数的测试服务验证判别力。

| 项目 | 对照组织                                                 | 生效证据与反例                                                                         |
| ---- | -------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| P02  | 同一明确调用任务，对照默认/自动设置与禁止设置。          | 对照能够发出调用，禁止组不发出调用；两组都不调用不足以证明禁止控制生效。               |
| P03  | 同一输入给出两个合法工具及全部参数值，分别指定 A、B。    | 实际调用随指定工具切换；不只重复执行题目已经强制要求 A 的单一请求。                    |
| P04  | 简单任务允许直接回答，比较未强制与 required。            | 强制组必须出现合法调用；若对照本来总调用，须补更有区分力的受控样例。                   |
| P05  | 同一明确双调用任务，对照允许多调用与禁止多调用。         | 已观察到对照产生多个调用，而禁止组最多一个；两组均为一个时生效证据不足。               |
| P06  | 固定复制任务，如 `A<CUT>B`，比较不设标记与设置 `<CUT>`。 | 对照完整产生标记及后缀，处理组保留前缀并在标记前停止；空响应或两组均提前结束不能通过。 |

不得用提示词控制替代对应接口参数。不假定 `parallel_tool_calls: true` 必须产生多个调用。[R1]

未收敛：对照样例完整输入、组数、重复次数、参数明确拒绝的归因，以及无区分力对照的终止规则。工具项“3 组 + 2 次复核”不自动成为本项已确认规则。未完成这些设计前，本节不能宣称可直接实现验收。

## 5. 最大上下文检测

### 5.1 已确认目标

只测当前接入模型服务支持的最大上下文窗口，单位为 token。主动寻找上限，不以固定若干档成功作为完成目标；不测长材料理解、最长输出或输出控制参数效果。

输出设置如为探测所必需，只作为固定测试条件。不能把固定输出设置下的最大可接受输入直接命名为模型总上下文窗口，不能把实际生成 token 数随意加到输入上当成容量。

### 5.2 探测方法提案

1. 固定计数来源和构造方法：记录 tokenizer 身份/版本、服务用量字段、消息封装开销与输出预留。计数来源不一致时先保留差异，不声称精确 token 容量。
2. 采用受控、低推理需求材料，从小输入逐步扩大，直到取得可归因于上下文限制的拒绝。请求要求极短回应，仅为完成探测，不评材料理解。
3. 在成功与明确容量拒绝之间缩小搜索区间；复核相邻候选点，记录分辨率和每侧多次结果。服务错误中报告的容量只能作为线索，不能独立作为实测值。
4. 分开识别网关体积限制、限流、连接故障和超时。未取得真正容量边界时停止并显示“未测出上限”，保留成功下界和停止原因。
5. 检查静默截断风险及计量口径。可研究少量位置标记或计数核对作为异常筛查，但标记正确不证明全部输入已保留，标记回答错误也不能直接判定截断；不发展成长材料理解评分。

设计提案的停止约束：必须固定实际请求总上限、最大输入构造量、单次超时和全局中止条件；任何上限触发都不等于测得模型容量。具体数值需要受控服务验证后冻结，本草案不采用无限增大或无限重试。

### 5.3 结论门槛

| 取得的证据                                             | 允许表达                                                                     |
| ------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 总窗口计量可解释，容量边界两侧有可复核证据，精度已固定 | 报告当前服务条件下的实测最大上下文及精度；存在区间时给区间，不伪造精确整数。 |
| 仅固定输出条件下的输入边界可靠                         | 详情报告输入边界；总上下文仍为“未测出上限”。                                 |
| 只获得成功下界                                         | “未测出上限”，详情保留已测下界。                                             |
| 计数不确定、疑似截断或被环境限制                       | “未测出上限”，说明证据缺口，不以厂商标称或模型自述补齐。                     |

未收敛：可靠计数适配、输入边界到总窗口的可验证关系、边界复核数量、精度和执行上限。这些是方法研究与校准责任，不要求用户提供业务样例，也不能据此降低已确认的产品目标。

## 6. 结构化输出支持

### 6.1 已确认范围

| 子项      | 验收对象                                               | 不评价什么                                           |
| --------- | ------------------------------------------------------ | ---------------------------------------------------- |
| 合法 JSON | 模型生成内容能否直接解析，不是 HTTP 响应外层能否解析。 | 不评价事实、抽取或推理正确性。                       |
| 指定结构  | 给定字段、必填项、类型、枚举及嵌套结构。               | 不以合法 JSON 替代指定结构符合性，不考业务填写质量。 |

### 6.2 测试方法提案

分别设计提示词要求、JSON 模式、指定 schema 模式的适用矩阵。明确记录当前用的是哪一种接口配置，不把仅提示词输出成功冒充原生结构约束模式支持。正式清单需固定所使用的 Chat Completions 配置，不混用 Responses 参数结构。[R2]

采用直接给出内容的复制/填表样例，不引入信息提取难度。只核验当前样例声明的 schema 子集，不宣称完整支持所有 JSON Schema 关键字或任意嵌套。

保留原始生成内容，以 parser 和结构校验器核验，不修补后判通过。JSON 空白、对象键顺序等合法差异不应被误判；具体解析器版本、重复键处理及等价性规则在正式说明冻结。

反例应包含非法 JSON、合法但类型不符、枚举越界、必填遗漏、嵌套不符、输出被截断及明确拒绝。区分模型生成不合规与测试设置造成截断，不把所有不完整输出都归为同一种错误。

未收敛：模式矩阵、完整 schema 和样例、样本数、复核次数、停止条件与拒绝归因；本项不继承工具项的次数为已确认值。

## 7. 消息与多轮输入支持

### 7.1 已确认范围

验证平台使用的不同角色消息能否接收，以及请求中携带已有对话后能否基于明确历史信息继续回答。不考复杂多轮推理、长期记忆，也不要求服务自动保存对话。工具结果回传不在本轮已确认清单内，不借本项恢复工具闭环测试。

### 7.2 测试方法提案

| 子项         | 简单样例方向                                                   | 结论边界                                             |
| ------------ | -------------------------------------------------------------- | ---------------------------------------------------- |
| 角色消息接收 | 为适用角色分别构造最小合法消息组合，检查请求接受与基本响应。   | 不把接受字段等同于角色优先级、抗冲突或指令遵循能力。 |
| 携带历史续答 | 在历史中直接给出虚构标识 `sample-42`，当前轮只要求复述该标识。 | 只证明已测历史组合的最小承接，不评价复杂记忆。       |

历史字段由测试程序明确随每次请求发送，不依赖隐藏会话。设计时固定历史消息排列、轮数、标识集合及回答验收，保持短且无歧义。

未收敛：平台角色子集的适用矩阵、合法组合、每组输入、次数和异常规则。没有另行授权把所有可见角色及多模态消息一并纳入。

## 8. 流式输出支持

本节对应新建的 [#40](https://github.com/relaxcloud-cn/llm-capability-doctor/issues/40)。

### 8.1 已确认范围

普通文本与工具调用两种场景都纳入：增量返回、完整组装、正常结束。不测速度、延迟、并发或性能稳定性，不执行工具或要求工具结果回传。

### 8.2 测试方法提案

| 场景     | 需要保留的观察                                           | 不能直接当成失败或通过的情况                                       |
| -------- | -------------------------------------------------------- | ------------------------------------------------------------------ |
| 文本     | 原始事件、实际内容增量、组装正文、结束证据。             | 收到 HTTP 成功或单个数据包不证明增量；空内容角色事件不直接算失败。 |
| 工具调用 | 调用分组、名称与参数片段、组装后的可解析调用及结束证据。 | 单个参数片段不必是完整 JSON；不能把不同调用片段串到一起。          |

工具调用分片依据 Chat Completions 对应规则组装，不用 Responses 事件名称替代。[R1] 传输分块、协议事件和实际内容增量分别记录；不使用网络分包数量作为通过门槛，也不要求每个事件恰好包含一个 token。

候选验收组覆盖正常文本流、正常调用参数分片、空增量、可区分的多调用、异常截断和解析错误。多调用组合是否沿用工具项样例及流式样本数属于方法提案，不冒充用户已确认的额外矩阵。

需要足够长且可控的输出，使内容增量可观察，但不进行最长输出探测。只得到单次完整内容时，记录未观察到可判定增量，不能仅凭短响应就宣称不支持流式。

结束规则应区分内容结束、协议结束、连接关闭、客户端主动停止和服务异常。表面字段差异由基线对比记录；只有关联实际组装或完成问题，才成为能力判定依据。正常事件顺序、结束标记与合法变体仍需按 Chat Completions 官方资料和受控样例冻结。

未收敛：完整事件序列样例、结束及异常归因、样本次数与复核、执行上限，以及无足够增量证据时的主结果表达。

## 9. 客户结果示例

以下为说明表达方式的虚构样例，不是任何真实模型的实测结果。

| 检测项             | 客户主结果       | 展开后的依据示意                                         |
| ------------------ | ---------------- | -------------------------------------------------------- |
| 单个工具调用       | 通过             | 已测基础参数样例满足要求；非流式条件及证据可定位。       |
