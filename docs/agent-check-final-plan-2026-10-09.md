目标是回答：**客户提供的模型服务，在本次验证的配置和负载下，能否支撑我们的 Agent 使用。** 重点解决结论不准、检测过慢、结果波动难解释、报告无法直接给客户看四个问题。

## 1 产品范围与交付

整个产品由 **5 组直接接口检测和 3 类 OMP 任务**组成。OMP 每类执行 2 次，共 6 次；检测组数不等于请求数，一个请求可以同时验证多个必要条件。

客户提供地址、模型名和密钥。检测配置由程序统一管理。支持 Chat Completions 和 Responses，每次运行选择其中一种，直接检测与 OMP 使用同一地址、模型和协议。完整接口地址可确定协议；仅提供基础地址时默认 Chat Completions，另保留显式协议参数用于 Responses 基础地址。运行前展示实际协议，不在失败后偷偷切换协议。

Windows、macOS、Linux 分别交付对应平台和架构的一个 CLI 可执行文件，内置固定版本的 OMP。首次运行自动校验、释放和启动内置程序，客户无需安装 Node、Python、Docker，也无需联网下载运行环境。不同平台使用各自的文件，不承诺一个二进制跨平台运行。接受 OMP 带来的包体积；最终文件大小以打包结果为准。

保留 Rust CLI。macOS 和 Windows 提供 GUI，均按第 1.3 节冻结原型实现；Linux 本版使用纯 CLI。三个系统使用相同检测内容、判定和报告，不让 GUI 成为 CLI 运行依赖。现有 GUI 只有 macOS 实现，Windows GUI 是本次新增交付，不能把旧代码已有桌面环境识别当成已支持 Windows GUI。CLI 自动生成客户 HTML 报告、机器可读结果和脱敏证据，生成这些文件不增加交付前需要安装的组件。

本版覆盖文本、工具调用和结构化输出。通用知识考试、开放式业务判断、图片音频、长历史压缩，以及额外的规则和权限测试均不纳入本版。这里验证模型需要的能力和真实 OMP 执行，不部署整个 allinone 产品。

## 1.1 CLI 入口与 GUI 启动：沿用现有流程

**用户已确认：新重构继续采用 `lbl/agent-check` 的启动流程，这部分行为不变。入口始终是 CLI，由程序检测桌面环境后自动选择 GUI 或纯 CLI。**

| 启动阶段 / 情况 | 保持的行为 |
| --- | --- |
| CLI 启动 | 读取服务地址、模型、密钥及检测参数，先做配置和连通性检查；检查失败在终端说明原因，不开始正式检测 |
| macOS / Windows 有可用桌面环境且 GUI 可用 | 自动启动对应平台 GUI，传递同一份配置；GUI 就绪后自动开始检测，客户无需重新填写配置或再次点击开始 |
| 无桌面环境 | 直接使用纯 CLI，终端展示检测进度和结果，并正常生成报告及证据 |
| Linux | 本版不提供 GUI，有无桌面均使用纯 CLI；显式请求 GUI 时说明本平台不提供 GUI 并继续纯 CLI |
| GUI 缺失或启动失败 | 在终端说明原因并回退纯 CLI，继续同一次检测请求，不重复启动两份检测 |
| 显式启动选项 | 保留 `--no-gui` 强制纯 CLI；保留 `--gui` 请求启动 GUI，不可用时仍回退纯 CLI；两者互斥 |

沿用现有桌面环境识别规则和窗口就绪确认机制，包括 SSH、CI、无显示环境的纯 CLI 路径。GUI 继续调用同一套 CLI 检测执行层，在后台执行时禁止再次唤起 GUI；配置与已有启动检查结果保持传递，避免重复检测。GUI 和终端消费同一套进度、判定和报告结果，GUI 不成为纯 CLI 运行依赖。

实现参照：[CLI 启动分流](../src/main.rs)、[桌面识别与原生 GUI 启动](../src/gui.rs)、[启动检查](../src/preflight.rs)、[GUI 接收配置并自动执行](../prototypes/agent-check-desktop/Sources/Model.swift)。保留的是以上启动行为；检测内容、判定和报告按本计划的新约定实现。

交付验收必须覆盖有桌面自动启动、无桌面纯 CLI、GUI 缺失/失败回退、显式启动选项、配置/连通性失败五类场景。核对无需重复填写或确认启动、只执行一份任务、两种展示方式的结果一致。不得把“先打开 GUI 再配置并手动开始”替换为默认流程。

### 必须还原的显示与行为

| 阶段 / 环境 | 保留的展示形式与新内容 |
| --- | --- |
| 启动 | 输出配置与连通性检查结果、桌面是否可用、最终采用 GUI 还是 CLI；报错说明原因。GUI 成功启动后按第 1.1 节交接，不在原终端另跑一份检测 |
| 纯 CLI 检测中 | 显示模型和脱敏地址；在同一区块刷新检测列表，每项显示等待、进行中或最终状态，运行项下方展示当前步骤；底部显示总进度和已用时间，保留颜色与转动提示 |
| 检测结束 | 保留结果汇总形式：运行状态、模型、脱敏地址、总用时、总体结论、逐项结果，以及实际生成的报告路径；失败说明与 HTML 使用同一套规则文案 |
| 日志重定向、管道或 CI | 沿用逐事件的纯文本输出，避免动画及光标控制字符；进度写入 stderr，机器可读 JSON 输出不混入进度文字；继续支持关闭颜色 |

检测列表替换为“接口与响应、工具调用、结构化输出、长上下文、并发性能测试、连续工具执行、工具故障恢复、多轮继续执行”8 项，与报告名称一致。OMP 三类任务各执行两次，显示真实执行次数和当前步骤；同时执行的任务都应显示进度，不沿用旧渲染器只记录一个活动任务的限制。等待、进行中、通过、不通过、未确认、未执行应明确区分；旧的“需人工确认”不能作为默认交付客户处理的状态。

进度由真实执行事件驱动，已用时间正常刷新；只有已知工作量才能计算相应完成比例，最大上下文等动态探测阶段显示当前动作和已用时间，不按时间虚增检测进度。任务数量、请求数量与检测项数量不混算，进度百分比不表示预计剩余时间。检测结束后若仍在生成报告，应显示“正在生成报告”；只有文件成功落盘才输出可用路径。实际取消或提前结束时保留已完成结果，未完成项目不得显示通过。

总进度按已完成检测项数计算，分母为本次启动时确定的检测项总数，不能因失败或停止缩小分母；默认全量检测为 8 项，进度条沿用基准的 24 格和百分比，同时显示“已完成 X / N 项”（默认 N 为 8）和已用时间。OMP 某一类的第一次执行完成，不代表整类检测已完成；两次之间没有运行任务时显示“等待下次执行”，不得继续显示转动的运行状态。进度到 100% 表示检测项处理完成，不等于全部通过；报告生成和文件写入仍按实际状态单独展示。

### CLI 1:1 验收要求

1. 将冻结 HTML 的演示事件作为受控展示样本输入真实终端渲染器，在固定等宽字体、字号和终端行列条件下，逐阶段核对文字、顺序、符号、配色、布局和刷新行为；保留启动、接口检测、两个 OMP 任务同时运行、等待下次执行、报告生成及最终结果的截图或录屏。网页外壳不纳入终端画面对照。
2. 覆盖原型的四种场景：无桌面纯 CLI、有桌面打开 GUI、GUI 启动失败回退 CLI、连通性失败停止。再验证 `--no-gui` / `--gui` 与第 1.1 节一致；GUI 成功交接不另跑一份任务，连接失败不输出能力检测结论。
3. 覆盖等待、运行、恢复、通过、失败、未确认、未执行、取消和报告写入失败；同时运行的两个 OMP 任务都可见，等待中的下一次任务没有假运行状态。使用真实进度验证，不以网页回放通过代替实际 CLI 验收。
4. 分别验证交互终端、逐行日志、无颜色和窄终端；原地刷新不刷满屏或残留旧行，日志无动画与光标控制字符，停止后动画结束。stderr 进度不污染 stdout 的 JSON，长中文结论可读，CLI、GUI、HTML 的结论和数值一致。
5. 确认报告文件成功落盘后才显示可用路径，退出后文件仍可打开；核对真实运行数据未混入演示值。提交对照截图/录屏、四场景检查结果和数据一致性记录，**未通过本节 1:1 验收，CLI 显示不得标记完成。**

旧题号、旧模块名和已取消的 AI 报告生成阶段不继续出现在正式终端输出中。未在原型中演示的异常状态使用同一套布局和符号体系，不能自行增加新的显示模块或更换终端风格。

### 数据与实现约束

总进度、已用时间、活动任务和每项状态读取与 CLI 同一份事件，沿用第 1.2 节的进度口径：分母不因停止或失败缩小，第一次 OMP 执行完成不等于整类完成，100% 不等于全部通过。原型中的固定 `63%`、`5 / 8`、两条历史记录和时间仅为展示样本，不能硬编码进正式逻辑。

正式历史记录来自本机真实保存的数据，模型名称和地址取自该次检测的配置，不能用当前模型配置覆盖旧记录。记录页和报告必须关联同一检测编号；“查看报告”和“下载”打开的是该条记录实际生成的文件，不得所有记录都指向原型的同一份示例报告。正式记录应在应用重启后仍可读取，提前停止仅保留已有事实，继续遵守第 4 节的结论优先级。原型内存数组和“重置演示”不作为持久化实现。

本节冻结原型已展示的工作台、停止状态、检测记录、检测完成页和新建检测表单交互。用户已确认完成页和新建表单，统一纳入 v3 基准并按 1:1、100% 实现；重新检测、新建检测和关闭窗口的行为均已确认。后续如修改已确认页面，须经用户评审后再更新冻结基准和校验值。原有布局继续保持 1:1。其他必要状态沿用相同组件与判定口径，不擅自增加新功能或改变已确认布局。GUI 记录中的报告内容、对照和下载证据仍按第 4.1 节独立验收。

**完成页冻结基准（已确认，v3 沿用）：** [打开检测完成页](gui-reference/agentcheck-gui-prototype.html#completed)，附[桌面截图](gui-reference/agentcheck-gui-completed.jpg)。在已确认的工作台外框内展示总体结论、直接原因、8 项完成情况与总用时；保留五项接口结果和三类任务结果，失败任务默认展开两次执行结果及具体差异。主操作为“查看报告”和“重新检测”，重新检测演示从 0 / 8 开始、使用新编号并保留旧记录。完成示例为 `AC-20261009-003`，关联[该次示例报告](gui-reference/reports/AC-20261009-003.html)。所有记录仅为本轮页面演示，不代表真实测试或生产持久化；预览状态切换和重置按钮不进入正式产品。v3 已启用完成或停止后的新建检测入口；检测和报告生成期间仍禁用，防止重复启动。

**新建检测表单冻结基准（已确认，v3）：** [打开表单](gui-reference/agentcheck-gui-prototype.html#new)，附[桌面截图](gui-reference/agentcheck-gui-new-detection.jpg)和[连接失败截图](gui-reference/agentcheck-gui-new-error.jpg)。以弹窗承载服务地址、模型名称、API Key 和接口协议；地址、模型沿用当前配置，密钥重新填写并默认遮蔽。协议提供自动识别、Chat Completions 和 Responses，按第 1 节规则显示实际协议及请求地址；完整地址与显式协议冲突时就地提示，不静默切换。

主操作“检查连接并开始”先校验字段再检查连接；检查期间锁定提交，仍可取消。连接失败保留填写内容并解释原因，允许修改重试，不产生模型能力失败结论。成功后关闭表单，以新编号开始全部 8 项检测，当前模型与服务地址同步更新，已有历史记录保持原配置与结果。取消返回原页面，不开始检测；取消或成功后清空表单密钥，密钥不得进入历史记录或报告。正式实现应把本次凭据安全传给执行器，不使用原型的定时演示代替真实连接检查。预览支持连接成功、密钥无效、无法连接、模型不存在和接口不匹配五种可选演示结果；演示选项与说明不进入正式产品。CLI 首次启动仍自动传入配置并开始，表单只用于后续新建检测，不增加首次启动步骤。

## 1.4 GUI 离线交付：选型调研与实施验证

**用户确认的优先要求：客户现场有受支持的桌面环境时，不能因为缺少开发工具或 GUI 运行库而打不开 GUI。Windows 范围为 Windows 10/11，不要求 Windows 7/8 或 Windows Server；macOS 继续提供 GUI，Linux 保持 CLI。** GUI 所需组件必须随交付物提供，不能依靠现场联网下载、让客户手动安装，或将缺依赖后的 CLI 回退视为 GUI 验收成功。

**用户已确认：保留 Rust CLI 和检测核心，GUI 使用 Electron。** 这是根据本产品的离线交付、已冻结 HTML 和跨平台维护要求作出的工程判断，不是已实测证明 Electron 在所有机器上更稳定。此前提出的 Rust + Tauri 2 + 完整 WebView2 作为调研对照保留，本版不采用，不同时维护两套 GUI。本节记录已确认的选型、依据和验证要求，尚未安装框架、替换 GUI 或验证 Windows 启动。

### 方案比较

| 方案 | 现场依赖与页面实现 | 主要代价 | 本产品的判断 |
| --- | --- | --- | --- |
| Rust 检测核心 + Electron GUI | GUI 随包携带 Chromium 和 Node.js，客户无需另装 Node 或 WebView2；Windows、macOS 可固定同一 Electron / Chromium 版本，并复用 HTML/CSS | 完整运行环境增加包体积，需要维护少量界面主进程代码和浏览器内核更新 | 本版采用：页面一致性与运行环境版本更容易统一 |
| Rust + Tauri 2 + Fixed Version WebView2 | 完整携带固定版 WebView2 后可以离线使用；macOS 使用系统 WKWebView | 需要处理 Windows 固定运行环境的路径和权限，同时验证两种页面引擎；不能继续按依赖系统 WebView 时的小包体估算 | 调研对照，本版不采用；完整打包也可满足免装依赖 |
| 原生 Rust GUI（例如 egui / eframe） | 不依赖 WebView2；使用自己的界面布局与绘制体系 | 已确认的 HTML/CSS 需要重新实现，还要验证字体、输入、图形后端和报告展示 | 本版不优先，增加 1:1 页面还原工作 |

Electron 的运行环境随应用分发见[官方介绍](https://www.electronjs.org/docs/latest/)；Tauri 的系统引擎选择见[进程模型](https://v2.tauri.app/concept/process-model/)；原生 Rust 候选的绘制后端见[eframe 文档](https://docs.rs/eframe/latest/eframe/)。表中维护成本与适配难度属于针对本仓库的判断，没有据此虚构性能分数、启动速度或内存对比。

### Tauri 调研对照中的部署约束

Tauri 默认 Windows 安装流程可能下载 WebView2；`embedBootstrapper` 也仍需网络。`offlineInstaller` 是离线安装运行库，`fixedRuntime` 才是携带特定版本，不能混称为“都无需安装”。这些配置描述的是安装包行为，不会自动把全部依赖变成一个可独立运行的 EXE。[Tauri 分发说明](https://v2.tauri.app/distribute/windows-installer/)

微软 Fixed Version 方案要求携带完整文件并指定运行路径；文档列出的文件体积超过 250 MB，不能当成最终压缩包大小。Windows 10 上 v120 及以后的非打包应用需设置相应 AppContainer 读取 / 执行权限；固定运行环境不能直接从 UNC 网络路径运行；WebView2Loader 还须静态链接或一同分发。因此，只把一个 Tauri EXE 交给客户仍不满足要求。[微软分发说明](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)

这些约束可以处理，但增加了本产品的部署适配工作；不能把它们说成 Tauri 天生无法离线，也不能宣称 Electron 自动免除所有系统权限和图形兼容问题。本版须实测 Electron 完整交付包的大小、释放耗时及运行内存；未做同条件对比前，不给两种框架下性能优劣结论。

### 已确认方案如何接入现有代码

1. **保留检测核心。** Rust 负责配置、HTTP 检测、OMP 调度、结果判定、报告及历史数据；Electron 负责窗口和已确认页面。通过受控进程通信传递配置、事件和操作，不在界面里复制判定规则，不引入需要匹配 Electron ABI 的 Rust / Node 原生扩展。
2. **整包内置。** 使用官方 Electron 分发工具生成包含支持文件的完整 GUI 目录，再由现有 Rust 启动器内置压缩并释放到本机用户目录。单文件指客户拿到的交付入口是一个文件，运行时仍会释放内部组件；不能只内置 Electron 主 EXE 或 `app.asar`。所有 HTML、CSS、脚本、图标及所需字体资源本地提供，客户端不执行 npm / Cargo / 在线组件安装。[Electron 打包说明](https://www.electronjs.org/docs/latest/tutorial/application-distribution/)
3. **补齐打包器。** 当前 `build.rs` 拒绝符号链接且只识别少数可执行路径，`src/runtime.rs` 的 GUI 路径写死 macOS App。按真实 Electron 分发目录扩展清单、可执行权限和平台入口；macOS Framework 内部链接仅允许经校验且目标仍在组件内部的相对链接，保留目录结构及签名，不取消路径穿越防护。发布前递归检查 CLI、GUI、OMP 和附带库的实际非系统依赖；Rust MSVC 程序优先静态链接 CRT，但仍核对最终导入表，不能把编译选项当作验证结果。[Rust 链接说明](https://doc.rust-lang.org/reference/linkage.html)
4. **保留启动与退出行为。** CLI 检查配置后唤起 GUI，界面加载和进程通信就绪后只启动一份检测。GUI 仍按第 1.3 节确认停止并保存再退出；纯 CLI 不启动 Electron。GUI 启动准备不得混入模型检测耗时。保留故障回退能力，但受支持桌面缺少交付依赖属于发布缺陷，不能用回退掩盖。
5. **按桌面应用发布。** 展示本地资源，保持渲染进程隔离与沙箱，关闭页面的 Node 直接访问，仅开放必要操作；报告中的模型内容按数据渲染。构建侧固定运行环境版本与校验值，完成 Windows 签名、macOS 签名和公证并验证提取后的程序；更新随新的完整离线包交付。保留关闭硬件加速的兼容路径并实测，不能靠关闭沙箱修复启动问题。[Electron 安全说明](https://www.electronjs.org/docs/latest/tutorial/security/)、[签名说明](https://www.electronjs.org/docs/latest/tutorial/code-signing)、[图形兼容接口](https://www.electronjs.org/docs/latest/api/app/#appdisablehardwareacceleration)

### 兼容范围与证据边界

Windows 10/11 的确认不等于所有系统构建号和 CPU 架构均已验证。整套产品的最低要求取 GUI、Rust CLI、OMP 的交集；例如 Bun 当前文档要求 Windows 10 1809 或更新版本并有 CPU 指令集要求，需进一步核对本产品固定 OMP 版本所内置的 Bun，而非只看最新 Bun 文档。macOS 暂不降低现有 macOS 14 最低要求。按操作系统和 CPU 架构分别准备产物，发布清单写明已实测的版本与架构，不依赖开发机上的模拟执行代替验收。[Bun 系统要求](https://bun.com/docs/installation)

这里承诺的是在列明的受支持环境中由我们解决软件依赖，不承诺绕过客户禁止执行软件的管理策略，也不把没有运行权限、磁盘空间或不支持的 CPU 说成可以通过携带 DLL 解决。本机及已有记录尚未提供新版 Windows GUI 的原生验收；现有发布记录中的 Windows 编译及 DLL 检查不能升级为 GUI 已可用的结论。

## 2 检测内容与通过条件

**直接接口检测**发送实际 HTTP 请求，按响应和工具交互事实检查，不使用另一台 LLM 评分。

| 检测组 | 检查内容 | 通过条件 |
| --- | --- | --- |
| 接口与响应 | 非流式、流式、消息历史、中文和响应结束 | 请求能按所选协议完成；文本和工具参数完整，错误、拒绝、截断不会被当成成功 |
| 工具调用 | 工具选择、参数内容、调用 ID、结果回传与继续执行 | 调用符合定义，参数对应真实输入；回传结果与调用关联正确，后续确实使用了工具结果 |
| 结构化输出 | 协议原生 JSON Schema 请求 | 服务接受原生约束，输出结构和字段值符合要求；单靠提示词生成 JSON 不算支持 |
| 长上下文 | 验证当前接入模型服务是否支持至少 128K 上下文，并继续探测最大容量；不做长材料信息提取检测 | 可靠实测证明支持至少 131,072 tokens 即合格；已确认最大容量低于该值则不合格，证据不足则未确认。达到最低要求后，最大上限未确认不阻止本项通过；只有最大值已确认，才显示“模型支持最大上下文为 X tokens” |
| 并发性能测试 | 4 并发下的完成情况、最长用时和平均用时 | 4 个规定负载的请求同时发出，每个在 60 秒内完整完成且结果合格；由同一批有效请求记录计算最长和平均用时，保留首次失败、重试和恢复记录 |

直接检测使用程序生成的数据、工具定义和可计算的结果关系，覆盖必要的嵌套对象、数组、枚举、必填项和字段绑定。复用已有请求中的协议、耗时和结束信息，不按每个检查条件增加一道题。

**OMP 任务**实际启动内置 oh-my-pi，开放原生 `read`、`glob`、`grep`、`write`、`edit` 文件工具，不用测试专用工具替换原生执行。

| 任务 | 执行内容 | 通过条件 |
| --- | --- | --- |
| 连续工具执行 | 读取 3 份文件，每份 4 条记录，汇总为结果文件 | 12 条记录完整，ID、负责人和版本对应正确，确有读取和写入证据，任务正常结束 |
| 工具故障恢复 | 在首次指定读取时返回一次明确可恢复的错误，之后恢复正常 | 错误真实传给模型；模型继续调用工具，最终正确汇总全部记录并正常结束 |
| 多轮继续执行 | 第一轮完成汇总；同一会话第二轮要求新增 1 条、更新 1 条，并保留其他记录 | 第一轮结果正确；第二轮得到正确的 13 条记录，更新生效、原有有效内容保留，正常结束 |

三个任务共用数据格式和验收程序：输入记录为 `id`、`owner`、`version`，输出为包含 `records` 数组的 `result.json`。来源快照由检测器保存，不允许待测模型改写验收依据。多轮任务在第一阶段验收后保存结果快照，再提供第二阶段变更。

程序根据来源快照和变更计算应有结果，再按 ID 比较实际文件。核对字段、类型、重复或遗漏记录、真实工具事件和最终结束状态；不以关键词、文件存在、模型声称完成作为通过依据。不要求固定调用顺序、固定文本排版或记录排列顺序。

每类两次使用相同数据和设置，但使用独立目录、独立会话。多轮任务内部的两轮共享会话。工具意外出错后自行纠正，只要最终结果正确、必要过程有证据、任务正常结束且未超时，可以通过，并记录恢复过程。任务已经失败后，另一次成功不能覆盖失败。

## 3 时间预算与运行条件

以下为当前确认的测量范围和运行要求：

| 项目 | 固定要求 |
| --- | --- |
| 上下文 | 最低要求 128K = 131,072 tokens，同时测量最大容量；包含系统、工具、历史、输入和预留输出。原先 256K 门槛及长材料信息提取要求不再采用 |
| 4 并发负载 | 每个请求约 32K 输入，实际生成约 1K 输出；不按探测出的最大上下文构造并发负载 |
| 单次请求 | 从第一次发起到完整接收共用 60 秒，包含排队、网络、等待重试和重试本身 |
| 接口重试 | 临时网络错误、429、5xx 额外重试最多 2 次，即总计最多 3 次尝试 |
| OMP 运行 | 共 6 次，最多同时运行 2 次；每个任务最多 240 秒，多轮任务两阶段合计计时 |

重试由统一请求层管理，关闭 OMP 叠加的自动网络重试。恢复后响应合格可以通过，但原始失败、次数和耗时必须保留；不得把已经超时的请求重新计时，也不得用重试抹掉语义错误。鉴权失败、参数不支持、格式或内容错误不做网络自动重试。模型在 OMP 内纠正工具参数，属于同一次任务内的正常恢复。

**以下为实现默认值，区别于用户明确选择的门槛。** 总耗时目标约 10 分钟，保护性上限 17 分钟：直接检测最多 240 秒，OMP 阶段最多 750 秒，清理和报告最多 30 秒。直接检测与 OMP 分阶段执行，4 并发测量期间不混入其他探测流量。总预算提前耗尽时保留已有结果，其余标为未完成，不伪造通过或模型失败。

OMP 两个执行位置按三批安排：连续①与恢复①、多轮①与连续②、恢复②与多轮②。每批最多 240 秒，另留 30 秒启动和退出余量。无需等所谓第一轮的三类任务全部完成后再开始第二轮。

计量默认值为 32K = 32,768、1K = 1,024，4 并发输入和实际输出各允许 ±10% 偏差。实际输出只计本次需要交付的内容，不用 `max_tokens`、内部推理或协议字节冒充。容量请求预留 1,024 输出 tokens，其余计入输入；记录实际输入与输出预留量，并据此确认容量边界。最大上下文探测也受直接检测的总预算限制；只探测到可用下限时，显示“已支持至少 X tokens，最大上限待确认”，不得将配置值、宣称值或当前最大的成功请求直接当作已确认最大值。

上下文先验证 128K 最低要求，再利用剩余预算探测最大上限。将“是否达到最低要求”与“是否已确认最大容量”分开记录：已验证下限达到 128K 即可通过，不因上限未找到而标为未完成；已确认最大容量低于 128K 则不通过；尚不能确认达到最低要求则为未确认。一个超过 128K 的请求被拒绝，不能直接证明容量低于 128K；网络错误、超时、预算耗尽和计量缺失也不能当作容量边界。精确容量边界必须有可靠计量及相应边界证据。

优先使用服务返回的实际 token 计量；缺失时，只有匹配该模型及消息编码方式的准确计数器才能补足。估算仅用于构造候选负载，不能用来宣布容量或负载通过。计量缺失、无法区分需要的输出或未构造出足够负载时，相关项标为未确认；直接检测预算内进行校准，预算耗尽不无限增加请求。

OMP 默认统一到已有发布清单的 18.1.13，打包脚本和运行时读取同一份版本及校验信息，消除现有两个版本来源的冲突。使用独立配置目录和会话，关闭无关插件、记忆、附加模型和后台网络任务，防止客户个人配置影响检测。参数和任务数据随检测版本固定并记录；固定设置减少外部差异，不承诺模型输出绝对不波动。

## 4 判定方式与客户报告

**判定输入是三样事实：原始请求响应、OMP 的实际执行记录、磁盘中的最终结果及来源快照。判定由共用程序完成，客户运行时不需要人工，也不需要额外的评分模型。**

每个结果使用通过、不通过、未确认、未执行四种状态。记录协议、检测版本、运行条件、每次尝试、任务编号、实际负载、耗时、原因和对应证据，避免各展示端自行猜测结论。

| 最终结论 | 条件 | 给客户的说明 |
| --- | --- | --- |
| 本次通过接入验收 | 全部必测接口项目通过（含已验证至少 128K 上下文），且 OMP 6 次全部通过 | 推荐按本次验证的协议、版本和负载接入；展示发生过的重试和工具恢复 |
| 本次未通过接入验收 | 存在已确认的不通过项或 OMP 任务失败 | 说明具体哪一步失败、对使用的影响和对应证据，不用平均分掩盖失败 |
| 本次未完成接入验收 | 没有已确认失败，但存在缺失证据、未确认或未执行项目 | 说明缺什么、为什么未测完，以及需要补做什么 |

已确认失败优先于其他未完成项。两次相同任务一成一败，最终不得推荐接入；两次都成功但发生恢复，仍可通过，报告必须展示恢复记录，不写成一次错误都没发生。

上下文已达到 128K 但最大上限未知，不属于阻止验收通过的未确认项；未能证明达到 128K 才按未确认处理。OpenAI 基线用于横向展示，不参与客户模型自身是否通过的判定，也不要求客户模型达到 Astra 的容量或耗时数值。

故障来源分清模型输出、服务或网络、接入配置、OMP 运行时、检测器自身。重试耗尽的服务错误或完整请求超时，可判相应服务检测不通过，但不能描述为模型理解能力不足。密钥错误、配置错误、检测器故障、启动环境缺失等没有取得有效能力证据的情况，标明阻断原因和未完成项目。

客户报告依次展示检测结论、逐项对比、问题与处理建议，页尾提供检测记录下载。取消笼统的模型总分，不把 6 次运行描述成长期稳定性保证。HTML、CLI 和现有 GUI 读取同一份版本化结果，由一处生成结论。**整份报告全部规则生成，不调用 AI 生成、润色、解释或改写报告内容；被测模型只参与接口检测和 OMP 任务执行。** 密钥不落入报告或日志，地址中的凭证和敏感查询参数脱敏。

交付前先检查检测工具自己会不会判错：正常完成、允许的记录重排、工具出错后成功修复，必须判通过；假装完成、字段写错、漏记录、遗漏第二轮更新、有效文件写出后异常结束，必须判不通过。恢复任务还需证明那次注入错误确实送达模型；否则不能宣称已测过恢复能力。

HTTP 自身验证覆盖两种协议中的结构约束拒绝、中文跨流片段、工具参数拼接、调用 ID 对应、截断、服务错误、重试预算和缺失 token 计量。检查结果不能因为相同错误在另一种协议里采用不同字段名而漏判。

然后在两种协议下分别连接真实模型，完整运行 6 次 OMP 任务，由我们人工核对实际过程和文件是否支持工具给出的结论。每种协议至少保留一组符合规定条件的真实模型完整通过记录，证明整套检测能跑通；真实失败也必须保留并核对，不能通过放宽阈值把失败改成成功。人工核对只用于研发验收，不能把发现的新误判交给客户处理。受控的脚本响应测试不能替代真实模型验证，旧测试专用工具的成功也不能替代原生工具验证。接口凭据在实施验收时通过安全配置提供，不写进计划。
