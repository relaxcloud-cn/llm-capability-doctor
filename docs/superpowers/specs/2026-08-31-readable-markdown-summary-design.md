# Markdown 报告可读性优化设计

## 背景

当前自分析 Markdown 的“能力分类检测结论”把分类下每个未通过项的
`failureCause` 直接拼接到同一个表格单元格中。连接错误、请求编号、URL
和内部字段名会重复出现，读者难以快速理解该分类的总体问题。

“并发响应明细”已经有总请求、成功、失败和平均响应时间汇总表，但随后
又逐条列出失败请求。失败请求的完整证据已经写入审计日志和失败 cURL
文件，Markdown 首屏不需要重复展示。

## 目标

1. 分类结论概括该分类下所有未通过原因，合并重复问题并标明影响项数。
2. 摘要使用简体中文业务表述，避免 URL、request ID、`transportOutcome`、
   `stderrExcerpt`、`passCriteria` 等内部术语。
3. 保留逐项技术原因在“42 项检测明细”、非通过项详情、JSON 和日志中，
   不改变检测判定或证据完整性。
4. 并发响应章节只渲染汇总表，不再渲染失败请求列表。

## 非目标

- 不修改采集请求、检测规则、模型自分析 JSON schema 或 PASS/FAIL 判定。
- 不删除审计日志、失败 cURL 文件或逐项明细中的技术信息。
- 不依赖 Markdown 阅读器对 `<details>` 等扩展语法的支持。

## 设计

### 分类失败原因归并

在 `src/analysis/orchestrator.rs` 的 Markdown 渲染层增加报告专用的原因归并
流程。输入是一个分类下所有非 PASS 的 `AnalysisTestResult`，输出是一个
短段落：

1. 先统计分类总项数、通过项数和非通过项数。
2. 对每个 `result_reason` 做原因归一化，删除证据定位噪声（URL、请求编号、
   `stderrExcerpt` 包装和重复的“期望/实际”前缀）。
3. 将可识别的根因映射为读者可理解的中文类别：
   - `transport_error`、`tls handshake eof`、超时、空响应：
     “请求连接中断或未返回有效响应”。
   - 自动工具选择参数被拒绝：
     “接口不支持当前自动工具选择配置”。
   - 工具调用闭环、结果关联或恢复失败：
     “工具调用流程未完成”。
   - 其他结构或字段不匹配：
     “模型返回结果与检测要求不一致”。
   - 无法归类时，保留经过长度限制和文本清理的原因首句。
4. 以归一化原因作为键去重并计数，按影响项数从高到低输出所有不同根因；
   同一根因只出现一次。
5. 渲染格式为：
   `分类共 N 项，P 项通过、F 项未通过。主要问题包括：原因 A（X 项）；原因 B（Y 项）。`

分类状态保持现有“通过/不通过”语义，避免改变已有报告消费者；若后续需要
区分“无法判断”，另行设计状态模型。

### 并发响应章节

保留 `concurrency_waves` 的汇总表（并发档位、总请求、成功、失败、平均响应
时间）。删除表格后的“失败请求”标题和逐条列表。`ConcurrencyFailure` 数据
结构暂时保留，因为 JSON/日志或后续报告可能使用；本次只移除 Markdown 投影。

### 数据流与安全

原始 `SelfAnalysisArtifact`、JSON 和日志不变。归并函数只在渲染 Markdown 前
运行，并继续通过现有 `markdown_cell` 转义表格内容。API Key 等敏感信息沿用
现有脱敏流程，不新增原文输出路径。

## 测试与验收

- 单元测试：构造包含重复连接错误、自动工具选择错误和结构不匹配错误的分类，
  断言摘要包含每类一次及正确计数，不包含 URL、request ID 和内部字段名。
- 单元测试：构造含失败请求的并发波次，断言 Markdown 包含汇总行但不包含
  “失败请求”、`request_id` 或具体错误文本。
- 回归测试：现有 Markdown、JSON、日志和报告路径测试继续通过。
- 手工检查：用现有 `deepseek-v4-flash` 证据重新生成 Markdown，确认分类摘要
  可在一两句话内读懂，技术细节仍可从“42 项检测明细”和日志追溯。

## 兼容性与回滚

变更仅影响 Markdown 文本渲染，已有 JSON、日志和 CLI 参数保持兼容。若摘要
归并规则产生误判，可回滚渲染层提交，不影响已生成的原始证据文件。
