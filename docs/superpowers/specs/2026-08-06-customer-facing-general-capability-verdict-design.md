# 客户视角通用能力结论模板设计

日期：2026-08-06

## 目标

让没有项目必需项配置的客户，在报告第一屏直接知道模型的通用能力是否通过、通过到什么边界、主要限制会影响什么。

结论必须稳定、可横向比较、可由结构化证据复算。报告不得仅按 PASS 比例评分，也不得让生成报告的模型自由决定总体等级。

## 非目标

- 不判断某个具体项目能否上线。
- 不输出百分制或加权分数。
- 不推断提供方身份、模型内部实现或未采集能力。
- 不改变 46 项逐项 PASS/FAIL 的证据规则。

## 通用能力等级

程序从 46 项最终状态确定性计算一个且仅一个等级：

| 等级 | 客户文案 | 判定条件 |
| --- | --- | --- |
| `PASS` | 通用能力通过 | 46 项全部 PASS。 |
| `CONDITIONAL_PASS` | 通用能力有条件通过 | 31 项基础必过项全部 PASS，但至少一个增强能力项 FAIL。 |
| `FAIL` | 通用能力未通过 | 任意基础必过项 FAIL。 |

等级不由 Skill 作者填写。`assemble_assessment` 根据逐项状态生成，`validate_assessment` 重新计算并拒绝任何不一致结果。

历史 evidence.v1 onsite/custom 日志可能没有完整 46 项。此时使用非判定状态 `NOT_ASSESSED`，客户文案为“通用能力未评定”，并明确显示已采集项数；它不属于上述通过、有条件通过、未通过三档，也不能被解释为能力失败。当前 evidence.v2 缺项仍由 parser 直接拒绝。

### 基础必过项（31 项）

- 接口与基础生成：`001`、`002`、`003`、`004`、`005`、`006`、`007`
- 结构化结果与基础上下文：`009`、`010`、`011`、`012`、`013`、`014`
- 基础指令与逻辑：`019`、`022`、`031`、`038`
- 核心工具链：`040`、`041`、`042`、`043`、`044`、`047`、`048`、`049`、`050`
- 基础性能与稳定性：`052`、`053`、`054`、`055`、`057`

这些项目覆盖接口接入、同步与流式生成、原生 Token 用量、基础 JSON 契约、最低上下文档位、精确输出、多轮修正、基础逻辑、单步与多步工具链、基础延迟、重复请求和固定并发。

### 增强能力项（15 项）

`008`、`015`、`016`、`017`、`018`、`020`、`024`、`033`、`034`、`035`、`036`、`045`、`056`、`059`、`060`

这些项目覆盖错误可观测性、更高上下文档位、复杂格式与摘要约束、Thinking/reasoning 可观察性、并行工具、百分位统计和安全业务词汇。增强项失败必须说明限制，但单独失败不把通用等级降为“未通过”。

基础项与增强项必须无重复、无遗漏地覆盖 collector 的全部 46 个保留检测项。测试直接将两组并集与 `RETAINED_TEST_IDS` 比较。

## 结构化输出契约

延续当前在途的 `reviews.v2` 与 `assessment.v6` 迁移，不再增加一个中间版本。`reviews.v2` 继续由 Skill 提供逐项判断、`verifiedFacts`、问题归并和边界；总体等级只出现在组装后的 `assessment.v6`。

在 assessment 的 `capabilitySummary` 中增加程序生成字段：

```json
{
  "generalVerdict": {
    "level": "CONDITIONAL_PASS",
    "label": "通用能力有条件通过",
    "passedTests": 40,
    "totalTests": 46,
    "passedCoreTests": 31,
    "totalCoreTests": 31,
    "passedEnhancedTests": 9,
    "totalEnhancedTests": 15,
    "statement": "本轮固定 46 项检测通过 40 项，31 项基础必过项全部通过；6 项增强能力存在限制，因此判定通用能力有条件通过。"
  }
}
```

`level`、中文标签、所有计数和 `statement` 均由程序按固定模板生成。assessment 校验器逐字段复算，防止手工篡改或文案与状态不一致。

`level` 允许 `PASS`、`CONDITIONAL_PASS`、`FAIL` 和历史不完整日志专用的 `NOT_ASSESSED`。`NOT_ASSESSED` 必须使用固定判定句：“本轮仅采集 `{collected}`/46 项，证据不足以生成通用能力等级，因此本轮通用能力未评定。”

现有 `headline` 保留为证据约束下的能力摘要，但降为总体等级后的说明文字；它不能覆盖或改写确定性等级。

## HTML 最终结论模板

“最终结论”保持在“检测信息”之后、各能力域表格之前，并成为报告最高信息优先级区域。固定顺序如下：

1. **总体等级**：显示三档中文标签，不显示百分制。
2. **固定判定句**：展示总通过数、基础项通过数、增强项限制数和总体等级。
3. **关键事实条**：固定展示 `通过项/总项`、接口协议、最高验证上下文档位、最高验证并发。
4. **客户说明**：展示已验证能力摘要，以及按影响排序的最多五个主要限制。
5. **证据边界**：保留边界和关联检测项，但视觉权重低于等级、事实和影响。

每个主要限制继续包含：标题、观察事实、能力影响、归因边界和检测项 ID。禁止把“没有独立 reasoning 字段”扩大成“模型没有推理能力”。

### 固定文案模板

全部通过：

> 本轮固定 46 项检测全部通过，因此判定通用能力通过。

有条件通过：

> 本轮固定 46 项检测通过 `{passed}` 项，31 项基础必过项全部通过；`{failedEnhanced}` 项增强能力存在限制，因此判定通用能力有条件通过。

未通过：

> 本轮固定 46 项检测通过 `{passed}` 项，其中 `{failedCore}` 项基础必过能力未满足，因此判定通用能力未通过。

历史不完整日志：

> 本轮仅采集 `{collected}`/46 项，证据不足以生成通用能力等级，因此本轮通用能力未评定。

> **综合结论：通用能力有条件通过**
>

## 数据流

1. parser 保持严格解析 evidence.v1/v2，不产生总体等级。
2. Skill 按现有规则固定 46 项 PASS/FAIL，填写 verified facts 和问题归并。
3. review validator 校验逐项证据、verified facts 和问题覆盖。
4. assembler 根据固定检测项集合计算 `generalVerdict` 并写入 assessment.v6。
5. assessment validator 独立复算等级、计数、标签和固定判定句。
6. renderer 只消费结构化 assessment，不自行重新解释证据。

## 失败与边界处理

- 解析失败、检测项缺失或引用证据无效时停止生成报告，不输出“未通过”来掩盖采集错误。
- 当前 evidence.v2 的 46 项状态不完整时 parser 拒绝输入；历史 evidence.v1 不完整日志生成 `NOT_ASSESSED`，不得套用三档结论。
- verified facts 为 `INCONCLUSIVE` 时事实条显示“未确认”，不得猜测协议、上下文或并发边界。
- 总体等级只代表固定通用检测标准，不代表具体项目上线结论。
- 原始 reasoning/thinking/signature 继续按现有规则保留；只脱敏凭证。

## 兼容与迁移

- collector 日志契约不变，仍支持历史 evidence.v1 和当前 evidence.v2；历史不完整日志保留报告能力并显示“通用能力未评定”。
- 完成当前在途 v6 迁移：同步更新 SKILL、evaluation rules、assessment schema、validator、renderer 和测试，消除代码已为 v6 而文档/schema 仍为 v5 的不一致。
- 已生成的静态 v5 HTML 不做原地迁移；使用同一源日志重新分析即可生成 v6 结论模板。
- 不覆盖当前工作树中已有的 dangling request ref 与 verified-facts 类型校验修改；实现应在其上增量开发。

## 验收与测试

1. 基础项与增强项集合无重复、无遗漏地覆盖全部 46 项。
2. 覆盖全部通过、仅增强项失败、基础项失败、两类同时失败和历史不完整日志五种场景。
3. assessment validator 能拒绝篡改的等级、标签、计数和固定判定句。
4. HTML 中最终结论只出现一次，顺序正确，四个关键事实可见，失败问题覆盖所有 FAIL。
5. 使用现有豆包日志重新生成报告，结果必须为 `40/46`、基础项 `31/31`、增强项 `9/15`、通用能力有条件通过。
6. Skill 全量测试、quick validation、凭证检查、自包含资源检查和打印样式检查全部通过。
